# ABCD 转译框架、分析哲学表达与勤益 AI 客服完整整合总说明

> 文档性质：本文件是原初构想、后续修订、分析哲学形式化、AI 客服专化要求和当前工程实现的统一制度说明。它不取代原始文档，而是为产品、开发、运营、审核和未来网站托管提供共同基线。
>
> 完整性边界：本文完整保留用户提出的语义要求及当前可观察系统事实，但不保存、复述或推断模型不可见的隐藏思维链。系统所称“思考过程”在可执行层一律落实为可观察的理由报告、证据引用、候选差异、审核意见、决策记录、工具调用摘要、运行指标和版本谱系。
>
> 保密边界：四个 Agent 的凭据只可存在于被 Git 忽略的本机 `.env` 或正式密钥管理系统。本文不记录任何密钥值。曾在聊天、截图或日志中暴露的密钥应吊销并轮换。

## 一、系统的根本目的

本框架首先是一个跨知识领域的转译组织，其任务不是简单改写句子，而是把一个领域中的专业知识、事实、限制和信息，转化为另一个领域或非专业受众能够理解、判断和行动的表达，同时保持原意、证据和边界。

在勤益 AI 客服中的具体目标依优先约束同时存在：

1. 保持事实准确，禁止以促成成交为由制造事实、确定性或承诺。
2. 促进有效询盘，但“促进”指帮助客户形成可继续讨论、可报价、可验证的需求，不是话术压迫或夸耀。
3. 给出与公司真实供给相连的产品方案。
4. 在普通聊天的合理时间内回复。
5. 控制模型和基础设施成本。
6. 塑造清楚、可靠、克制而专业的公司形象。
7. 让不懂 AI、也不懂网站编程的人能够通过傻瓜式界面理解和经营这套系统。
8. 为未来的网站运营托管保留空间，但不把“托管”理解为取消人类责任、最终审核和经营控制。

## 二、组织本体：四个独立 Agent 组成的公司

### 2.1 不是角色轮换，而是组织分工

A、B、C、D 是四个独立 Agent 岗位，不是同一个 Agent 在一条提示词中依次扮演四种角色。它们可以暂时运行在同一进程，也可以以后迁移到四个独立进程、服务或模型提供方；组织上的身份、上下文、权限、API 窗口和通信边界必须始终分离。

这套结构类似一个部门化公司：每个员工有自己的小规则和职责，部门之间通过制度化接口交接产品；公司还有高于岗位小规则的共同章程。岗位的原始产出可以体现岗位自身规则，但该产出能否成为下一环节输入或最终对客产品，必须接受公司制度和指向该产品的其他岗位规则约束。岗位冲突由 A 调节，硬性准入由公司制度执行，最终业务责任归人类。

### 2.2 固态与液态

- A 是不断容纳、保持组织连续性的“固态”：保存制度、历史、证据、版本和决策，但不亲自生成客户正文。
- B 与 C 是随具体任务和阶段变化的“液态”：在任务中读取获准的相关资料，完成生成或审核，然后释放任务上下文；不各自长期私藏另一部门的信息。
- D 是周期性反思和组织学习的“结晶过程”：比较一阶段内的工作，提出可能的方向和 Skill 改良，但不能自行改变生产规则。
- 公司准入层是制度执行机制，不是第五个 Agent。它验证通信路线、硬门槛和发布资格，任何 Agent 都不能通过提示词覆盖它。

### 2.3 四个岗位总表

| 岗位 | 组织身份 | 核心输入 | 核心输出 | 明确禁止 |
| --- | --- | --- | --- | --- |
| A：总体、协调、裁决 | 持久控制与制度记忆 Agent | 客户任务、动态合同、证据、B 候选、C 结果、D 提案、历史结晶 | 工作单、上下文授权、发布/返工/停止/转人工裁决、Skill 审批意见 | 不写客户正文；不替 C 审核；不要求 C 为经营目的放行 |
| B：转译、生成 | 产品生成 Agent | A 工作单、B1、B2、合同状态、允许证据、对应历史经验 | 候选回复、证据映射、显式理由报告、执行日志 | 不裁决自身是否合格；不查看 C 的私有审核历史；不覆盖硬门槛 |
| C：独立审核 | 产品质量与风险 Agent | A 发出的匿名候选、C1、C2、合同、独立证据 | `pass`、`fail` 或 `escalate`，问题清单、理由和修复要求 | 不生成替代答案；不继承 B 的隐藏上下文；不为 A 的经营决定降低标准 |
| D：阶段总结与改良 | 组织学习 Agent | A 发出的脱敏阶段快照、指标、候选和审核结果的可观察记录 | 阶段总结、候选比较、方向建议、Skill 变更提案、评测要求 | 不介入实时客户回复；不直接更新生产 Prompt、Skill 或知识库 |

## 三、公司宪法与岗位小规则

### 3.1 规则层级

由高到低为：

1. 法律、客户数据权利和人工最终责任。
2. 公司宪法与不可绕过的程序性准入规则。
3. 已验证的事实、证据、合同和硬门槛。
4. A 对本次任务作出的合法程序裁决。
5. B1/C1 等岗位基础合同。
6. B2/C2 等任务扩展。
7. 客户类型、国家、语言、渠道、预算、紧急程度、老客户身份和业务员临时要求等情境信息。
8. 文风、长度、措辞等软偏好。

低层规则不得覆盖高层规则。尤其是客户类型、国家、语言、销售渠道、预算档位、紧急程度、老客户身份和业务员临时要求，均不得覆盖 B1。

### 3.2 “输出不受大规则影响，产品受大规则审核”的精确定义

岗位可以在其局部章程内形成原始产出，公司层不应悄悄改写成另一个岗位的产出；但原始产出不等于可发布产品。公司层可以拒绝路由、拒绝发布、要求返工或转人工。这样既保留部门独立性，又确保制度不会只停留在提示词声明。

### 3.3 不可关闭的准入

- 未达到所需审核条件的候选不能发布。
- C 未通过时，A 不能直接发布。
- A 所谓“破例”只能是补证据、澄清合同或改变 B 的合法工作条件，使 B 重新生成一份能够按原标准通过 C 的产品。
- A 不得为了“破例”而驱动流程，更不得命令、诱导或配置 C 放行。
- 事实、金额、交期、合规等硬门槛，任何模型均无权覆盖。
- A 的接受只赋予组织程序上的可发布性，不自动赋予命题真理性。

## 四、A：总体、协调与裁决 Agent

### 4.1 A 的职责

1. 接收客户任务和运行环境信息。
2. 编译本次动态语义合同。
3. 确定合同字段状态、风险等级、需要的证据和执行路径。
4. 只向 B、C、D 发放各自所需的最小上下文。
5. 保存 ABCD 的可观察工作记录、理由报告、执行日志和结果。
6. 根据审核结果决定发布、返工、停止或转人工。
7. 在部门冲突时依据证据、制度和业务目标作出程序裁决。
8. 审议 D 的提案；需要时提交人类审批、安排评测和回滚方案。
9. 管理每个岗位、方向和领域所对应的资料库、经验库与 Skill 版本。

### 4.2 A 的限制

A 不参与客户内容生成。A 可以提出工作目标和边界，但不能代写 B 的答案；可以要求 C 审核，但不能替 C 判定；可以选择 D 的建议方向，但不能把未评测提案自动送入生产。

### 4.3 A 的上下文压缩

A 的活动上下文不断进行蒸馏和抽摄：旧的长上下文被压缩为可调用结晶，以控制上下文长度；结晶替代旧原文在活动上下文中的位置，但不删除原始记录。原始数据与结晶同时进入库，并通过谱系相连，以便在符合权限的情况下回源。

## 五、B：转译与产品生成 Agent

### 5.1 B1：预设语义合同

B1 是 B 的基础、不允许被情境字段覆盖的岗位合同，至少包括：

- 保持事实和约束，不把未知改成已知。
- 面向指定受众完成领域转译，解释必要概念，避免无意义术语堆叠。
- 将专业知识转成普通采购能够理解并采取下一步行动的表达。
- 依据证据建立需求与供给的真实连接。
- 区分事实、条件、建议、假设和待确认项。
- 对价格、MOQ、交期、产能、可行性、认证、合同等硬门槛保持条件化或转人工。
- 不利用客户身份、预算、紧急程度或临时销售指令绕开上述义务。
- 只使用 A 授权的知识、工具结果和会话资料。
- 生成附证据映射的候选，而不是自行宣布答案已获准发布。

### 5.2 B2：结构化可变需求

B2 初始空置，用来承载每次会话和任务中的更多需求，例如输出语言、中英双语、受众知识水平、客户类型、国家、渠道、预算档位、紧急程度、是否老客户、是否专业咨询、目标篇幅和经授权的业务员要求。

B2 可在对话中变化，但只能通过结构化白名单进入，不能接受任意 `customPrompt`。B2 永远不能覆盖 B1。

### 5.3 B 的历史信息

B 不把自身所有历史无限装入每次运行，也不拥有 C 的审核历史。B 在执行任务时可以从 A 的 B 专属库中读取与领域、方向、客户问题和当前合同相对应的脱敏经验、已批准 Skill、过往错误模式和必要原始记录。返工时 B 只获得该返工分支允许的信息。

## 六、C：独立审核 Agent

### 6.1 C1：预设审核语义合同

C1 至少检查：

- 是否忠实于客户已经明确的需求。
- 是否把 `provisional`、`unknown` 或 `conflicting` 信息误写成确定事实。
- 是否有证据支持产品、规格、金额、交期、能力和合规陈述。
- 是否遗漏关键限制、条件、风险或必要追问。
- 是否存在跨语言重要规格误译。
- 是否符合普通/专业模式的长度和表达要求。
- 是否触碰应转人工的退款、赔偿、投诉、法律或合同决定。
- 是否存在提示注入、越权、数据泄漏或跨客户信息使用。

### 6.2 C2：结构化可变审核需求

C2 初始空置，用于未来填入经过批准的特定国家、渠道、产品、法规或临时审核要求。C2 与 B2 一样可以演变，但不能降低 C1 或硬门槛。

### 6.3 独立性

C 不拥有 B 的生成思路、分支身份和私有工作说明，也不读取 B 专属历史。C 接收 A 发出的匿名候选、合同、证据和审核任务。C 可以拥有自己的审核理由报告和日志，并由 A 保存；B 不能直接读取 C 的完整内部记录。

## 七、D：阶段总结、比较与 Skill 治理

### 7.1 D 的任务

D 不做逐条实时审核，而是在阶段边界上使用 A 保存的脱敏信息：

1. 汇总阶段内成功、失败、转人工、延迟、成本和投诉模式。
2. 比较 Fresh-1、Fresh-2 与 Repair 的质量、错误类型和通过路径。
3. 判断问题来自知识缺口、合同编译、B 生成、C 审核、工具、模型还是制度。
4. 提出下一阶段的改良方向。
5. 蒸馏候选 Skill，并说明适用范围、证据、风险、评测和回滚条件。

### 7.2 触发条件

- 每周一次。
- 每累计 100 次有效对话一次。
- 连续出现同类错误时被动触发。
- 发生重大投诉时被动触发。
- 模型或知识库更新时被动触发。

自动更新必须考虑是否会耽误生产与工作。D 的计算应异步、限流、可暂停，不占用实时回复的关键预算；生产繁忙时可以延期形成提案，但不得静默取消或自动生效。

### 7.3 提案而非自动改写

D 的结果固定为 `awaiting_human_approval`。A 决定是否采纳方向；涉及生产规则、知识、Prompt 或 Skill 的变更还必须经过人类批准、离线评测、小范围发布、监控和可回滚。D 不能读取正在生成中的会话并即时改变该会话规则。

## 八、需求—供给“虚化、模糊、嵌合、硬化”方法

这里的“虚化/模糊”不是含糊表达或弱化事实，而是暂时抽去两侧表面叫法，把需求和供给转换成可比较的功能、约束和接口。

完整过程为：

1. 客户通常是工厂或组织客户，往往先有既定需求，再寻找能够接手的工厂。
2. 从客户话语中抽取用途、数量、尺寸、材料、性能、工艺、交期、预算、目的地、认证和决策状态。
3. 将尚不明确的需求保留为变量、区间、功能目标或待确认项，不擅自补值。
4. 将公司供给从宣传式描述转换为有证据的能力、条件、限制和需人工确认事项。
5. 在两侧寻找真实可对接点，例如用途与材料特性、数量与 MOQ、设计目标与工艺能力。
6. 先把连接点接上，形成候选方案和最少必要追问。
7. 随客户确认和证据增加，把模糊连接点硬化为明确、标准化、可生产、可报价、可验收的规格。
8. 如果客户需求本身不明确，则主动帮助其转成可生产规格。
9. 把公司资料转成销售方案时，目标是最清晰地传达自身条件和可能性，不夸耀、不伪造优势、不以此强迫成交。
10. 对普通采购解释印刷专业知识；需要时进行中外语言转译，并对重要规格启动独立审核。

## 九、动态语义合同

### 9.1 合同不是静态表单

合同是 A 对当前会话中客户命题、任务目标、证据和约束的可修订模型。每次会话或推理都可能使其变化；客户明确提出的点应硬化，客户未明确的点应保持推敲，而非笃定。

### 9.2 五种状态

| 状态 | 含义 | 允许的表达与动作 |
| --- | --- | --- |
| `confirmed` | 客户明确提出，或有有效证据确认 | 可作为当前合同约束；仍需标记来源和版本 |
| `provisional` | 暂定推断、候选方向或有条件成立 | 必须用条件化语言，并可继续追问 |
| `unknown` | 没有足够信息 | 不得补造；追问或说明无法确定 |
| `conflicting` | 多个来源或陈述互相冲突 | 停止硬化，展示冲突并请求澄清/人工核验 |
| `superseded` | 已被客户或有效新证据明确替代 | 不用于当前决策，但保留历史和替代关系 |

### 9.3 状态迁移

- `unknown -> provisional`：形成有根据的候选，但尚未确认。
- `unknown/provisional -> confirmed`：客户明确确认或授权证据确认。
- 任意活动状态 `-> conflicting`：发现无法自动消解的矛盾。
- `confirmed -> superseded`：客户明确修订或权威证据更新；新值建立为活动状态。
- 数据错误更正不能只改结晶，必须更正/封存原记录并级联撤销依赖旧值的结晶。

### 9.4 规范合同的完整字段与冻结规则

每个任务只有一份由 A 托管的规范合同作为语义与验收真源。除五种字段状态外，合同还应包含：核心命题，因果与推论关系，数字、单位和数量范围，模态强度，前提、适用范围、例外与反例，不确定性与风险，必须保留/允许省略内容，类比边界，源领域、目标领域、受众、用途、证据要求、风险等级，以及合同 ID、版本、哈希、父版本和谱系。

合同跨轮可变，但单次执行版本必须冻结；运行中不得无痕原地改写。新信息到达后建立新版本，重新编译 B/C 投影并记录迁移原因。两项硬规则不可同时满足时，合同编译应失败并交 A 或人工裁决，不能让 B 自行选择牺牲哪一项。

B2 中的每项硬要求都必须映射成 C 的可检查条件；C2 中会使候选失败的内容条件必须在生成前进入 B 可见的规范。C 可以保留具体审核方法的独立性，但不得在生成后新增事先不存在的验收义务。

## 十、风险、硬门槛与证据

### 10.1 必须受控的硬门槛

价格、MOQ、交期、产能、生产可行性、模具可行性、工艺可行性、认证、合同、付款、退款与赔偿、订单隐私、物流状态、法规、客户要求的精确性能，以及任何跨语言的重要规格翻译。

这些字段不得由模型常识或推测确认。必须有当前有效证据、工具结果或人工确认，并受合同状态约束。退款审批、赔偿决定、投诉裁决和法律事项直接进入人工流程。

### 10.2 证据等级

- 已审核知识库条目：可作为对客事实来源，但受版本、地区、产品和有效期限制。
- 受控业务工具结果：例如经租户和用户归属校验后的订单状态，只能最小化提供。
- 客户本轮明确陈述：用于其需求合同，不自动证明公司的供给能力。
- 脱敏经验和 Skill：指导过程与表达，不是事实来源。
- 模型既有知识、历史相似案例和销售偏好：不能单独支撑硬门槛。

### 10.3 提示注入和越权

任何要求忽略公司规则、泄露系统提示、跨客户取数、读取原始联系方式、伪造证据或绕过 C 的指令均视为安全风险。它们不进入 B2/C2，也不能改变规则层级。

## 十一、完整执行状态机

### 11.1 普通路径

1. 接收并校验输入、身份和会话。
2. A 编译/更新动态合同，识别语言、受众、风险和所需证据。
3. 查询允许的知识和工具；无可靠证据时不猜测。
4. 普通咨询只运行 B，形成候选、证据映射和可观察理由报告。
5. 公司层执行确定性预检 C0，包括格式、长度、无依据断言、硬门槛和安全检查。
6. 低风险且 C0 通过时，A 可作发布裁决。
7. 高风险、安全风险或 C0 首次不通过时，启动独立 C。
8. 达到相应审核条件且公司准入通过后发布；否则进入返工或人工接管。

这里“普通咨询走 B”是为了速度和成本，不表示没有公司层确定性检查。独立模型 C 只在风险或失败条件出现时运行。

### 11.2 独立 C 的启动条件

- 命中任一硬门槛或高风险领域。
- 发现提示注入、权限或数据安全风险。
- B 候选首次没有通过确定性预检。
- 返工后的三个候选均必须分别接受 C 审核。

### 11.3 B 与 C 的信息交流

从制度上，B 与 C 不直接互发任意消息。交接必须是：`B -> A -> C`，审核回传为 `C -> A`；需要返工时 A 只把获准的信息送给 B。B 能获知的是“是否通过”和经 A 过滤的结构化原因，而不是 C 的全部上下文或私有历史。

固定通信路线：

```text
A -> B  work_order
B -> A  candidate
A -> C  review_request
C -> A  review_result
A -> D  stage_snapshot
D -> A  stage_proposal
```

任何未列出的路线由通信总线拒绝。所有结果必须回到 A。

## 十二、三候选返工与重新审核

C 首次不通过后，同一返工轮次产生三份彼此有意义区分的候选：

1. `Fresh-1`：完全重新生成，不读取旧稿，也不读取上次审核原因。
2. `Fresh-2`：另一份完全重新生成，同样不读取旧稿或上次审核原因，并使用独立随机性/策略以增加解空间差异。
3. `Repair`：可以读取旧稿和 A 过滤后的结构化审核问题，针对问题改良。

C 对三份内容执行两层工作：

- 分别重新审核：每份从零应用 C1/C2、合同和证据，不因上次结果预设结论。
- 基于历史审核信息的比较：分析新旧错误是否消失、出现或转移，并比较三份候选的证据、合同忠实度、风险和表达质量。

比较结果属于 D 的阶段信息。C 的单份审核判定仍保持独立，不得因为“三选一”而放宽标准。A 只能在已通过的候选中依据目标函数选择；如果没有候选合格，进入下一轮或转人工。

## 十三、失败计数、停止条件与人工接管

- 自动返工是有界的，不能无限循环。
- 连续三个失败轮次后自动转人工。这里按完整审核轮次计数，而不是把同一轮的三候选机械算成三次失败。
- 退款、赔偿、投诉、法律事项、明确人工请求、权限不足、重大证据冲突或系统被暂停时可不等待三轮，直接转人工。
- 到达回复截止时间但无法完成必要审核时，返回简短且不作未经审核承诺的说明，并视情况建立人工服务请求。
- 截止时间触发后必须取消本轮发布资格。任何迟到候选不得再发布、不得写入当前会话的已接受状态，也不得产生迟到准入、计费或治理副作用；必要的超时审计事件除外。

人工接管报告应包含：

1. 客户原始目标和当前意图摘要。
2. 已知字段及其五种合同状态。
3. 已确认事实、证据 ID、来源和时效。
4. 未知项、冲突项和已被替代项。
5. 已尝试候选、各轮失败原因和风险。
6. 客户语言、渠道、紧急程度与专业咨询模式。
7. 需要人工决定或联系客户的问题。
8. 不应自动承诺的硬门槛。
9. 会话和事件追踪 ID；避免不必要暴露原始联系方式。

## 十四、三层记忆、总库与即时调用库

### 14.1 L0：当前会话

- 内容：当前任务合同、最近对话、当前证据、运行状态。
- 访问：当前会话自动访问。
- 生命周期：服务于实时工作；会话删除时删除或封存其派生关系。

### 14.2 L1：即时调用库/结晶库

- 内容：从历史记录蒸馏、脱敏、分类并保留谱系的经验结晶、错误模式、合同模式和已批准 Skill 索引。
- 访问：脱敏后的 L1 经验可自动访问，并按岗位、领域和任务做最小召回。
- 作用：替代长原文进入 A 的活动上下文，降低成本和噪声；不替代总库中的原始记录。

### 14.3 L2：总库/强库

- 内容：ABCD 的全部可观察原始事件、输入输出、理由报告、执行日志、证据引用、版本、审核和裁决，完整且加密归档。
- 特性：相对于 L1，L2 在授权范围内保持原始可观察信息的完整性，不把蒸馏当作原文的替代品。
- 默认保留：无期限归档。
- 例外：客户删除、授权撤回、法律要求和数据错误更正可触发删除或封存，并级联撤销相关结晶。

### 14.4 访问矩阵

| 行为 | 自动允许 | 条件式回源 | 必须人工批准 |
| --- | --- | --- | --- |
| 当前会话读取 L0 | 是 | - | - |
| 读取脱敏、相关的 L1 经验 | 是 | - | - |
| L2 单个会话原始记录 | 否 | 仅投诉、人工接管、证据冲突或审计 | 异常访问或超出既定目的时需要 |
| 跨客户检索 | 否 | 否 | 是 |
| 批量读取 L2 | 否 | 否 | 是 |
| 原始联系方式 | 否 | 否 | 是，并需业务合法性 |
| 历史订单 | 否 | 只读订单工具按当前身份最小查询 | 跨订单/批量需要 |
| 抽取 D 的训练数据 | 否 | 否 | 是 |

A 不是无限制的超级用户。A 访问 L2 若出现异常模式、范围扩大或越过单会话合法目的，必须取得人工批准并留下审计记录。

### 14.5 原始记录、结晶和谱系

每个结晶至少应记录：来源事件 ID、时间范围、租户/会话匿名范围、蒸馏版本、生成岗位、审核状态、适用领域、有效期、撤销状态和依赖关系。删除、更正或撤销源数据时，所有依赖结晶应失效、重算或封存，禁止留下“幽灵事实”。

L1 必须能够从 L2 重建。结晶是有损、可回溯、可被新证据击败的抽象表征；不能无限进行“摘要的摘要”。重要更新应同时参考原始记录与旧结晶。数字、单位、风险警告、严重缺陷、人工否决和未解决争议不得在蒸馏中被压掉。

建议的结晶制度状态为 `draft`、`validated`、`active`、`superseded`、`revoked`。这些状态与客户合同五状态属于不同层次，不得混用。

## 十五、理由报告、日志与思维过程的工程化边界

用户要求 A 保存 ABCD 的自然语言内心推理、思考过程和日志。工程上应完整保存系统可取得和可以合法处理的显式材料：

- Agent 自己输出的理由摘要、假设、证据和不确定性。
- 输入合同和上下文版本。
- 工具调用名称、最小参数摘要、结果 ID 和耗时。
- 候选正文、审核决定、问题代码、修复建议。
- A 的程序裁决、D 的阶段比较和 Skill 提案。
- 模型、Prompt、章程、知识和代码版本。

显式理由报告建议使用统一结构：`Observation`（观察）、`Hypothesis`（假设）、`Alternatives`（备选）、`Evidence`（证据）、`Decision`（决定）、`Uncertainty`（不确定性）和 `Action`（行动）。另设 `ExecutionTrace` 记录事实上调用了什么、使用了何种权限、输入了哪些版本、耗时和结果状态。

档案必须区分外部事实、Agent 观察、Agent 显式理由、系统执行事实、C 审核结论、A 正式决定和 D 改良提案。自然语言理由不能仅因被记录就自动提升为事实、结晶或 Skill。

不得声称能够取得供应商模型未返回的隐藏内部思维链，也不应为了“完整日志”要求模型暴露冗长私密推理。这样既保持可审计性，也避免把不可验证的叙事当作真实认知过程。

B 的生成记录存入 A 的 B 专属分区，C 默认不拥有；C 的审核记录存入 A 的 C 专属分区，B 默认不拥有。A 按最小权限路由，D 只接收脱敏阶段材料。

## 十六、知识库、经验库与 Skill

### 16.1 三者不能混同

- 事实知识库：产品、规格、工艺、认证、政策等可对客事实，必须有来源、审核状态和时效。
- 经验/日志库：工作事件、失败、客户互动结构和审核记录，受隐私、访问和保留制度约束。
- Skill：从重复成功与失败中蒸馏的程序性能力，例如合同编译、普通采购解释、三路返工或规格翻译审核；Skill 不能作为事实证据。

### 16.2 A 内部的分类小库

A 的库按 B/C、方向、领域、语言、产品、风险和版本分门别类。B 与 C 各自保留对应的已批准 Skill 清单，执行时再由 A 提供相应数据和历史；它们不各自维护彼此冲突的永久事实库。

### 16.3 Skill 演化

B/C 的候选 Skill 随数据累积而变化，但变化发生在 D 的阶段治理中。每阶段结束后：D 提案，A 审议，人类批准，评测通过，形成新版本，再影响下一阶段的 B/C。所有版本可回滚，旧版本保留适用期和淘汰原因。

## 十七、分析哲学形式化表达

### 17.1 基本对象

设客户任务为 `T`，证据集合为 `E`，动态合同为 `K_t`，B 的候选为 `x`，C 的审核关系为 `R_C(x, K_t, E)`，公司准入关系为 `P(x)`，A 的裁决为 `J_A`，D 的阶段提案为 `G_D`。

合同不是单一命题，而是带状态的命题集合：

```text
K_t = { <p_i, s_i, source_i, version_i, time_i> }
s_i in {confirmed, provisional, unknown, conflicting, superseded}
```

### 17.2 转译作为约束保持映射

从源领域语言 `L_s` 到目标受众语言 `L_t` 的转译不是单纯同义替换，而是映射：

```text
F: (T, K_t, E, audience, purpose) -> x
```

合格转译要求：

1. 相关命题内容在允许的抽象层级上保存。
2. 模态强度不被非法增强，例如“可能”不能变成“必然”。
3. 证据依赖、条件和未知项仍可追踪。
4. 目标受众能够理解并据此采取合适行动。

语义不变量至少包括：

- `P`：核心命题与指称。
- `R`：推论关系和因果结构。
- `Q`：数量、单位、量化范围。
- `M`：模态强度，如可能、应当、必然。
- `C`：条件、前提和适用范围。
- `D`：反例、异议和击败条件。
- `W`：风险、警告和不可省略限制。

表达形式可以改变，但不得无授权改变指称、真值条件、因果方向、量化范围和模态强度。类比只是一种局部结构映射，不表示两对象在本体上同一；类比失效处必须说明。

### 17.3 语义合同与可废止性

多数客服命题是可废止推理：新证据到来时结论可修订。因此 `provisional` 不是较弱的 `confirmed`，而是具有不同推理许可的状态。开放世界假设适用于未明确字段：数据库中没有值不蕴含否定，也不蕴含任意默认值。

### 17.4 需求—供给嵌合作为部分同态

设客户需求结构为 `D_c`，公司能力结构为 `S_q`。虚化是分别提取功能与约束结构 `alpha(D_c)`、`beta(S_q)`；嵌合是在证据许可下寻找部分映射：

```text
h: alpha(D_c) ⇀ beta(S_q)
```

`h` 只在双方存在真实接口的子域上定义。硬化是把经客户确认和证据支持的映射编译成生产规格 `Spec`。不存在接口时应留下未定义，不得通过语言粉饰伪造全映射。

### 17.5 认识论分工

- B 承担构造性任务：提出候选表达。
- C 承担反驳性任务：寻找违反合同、证据或规则的反例。
- A 承担制度性任务：分配权限、协调冲突并决定组织行动。
- D 承担二阶任务：比较一阶活动并提出规则修订。

这种分工降低同一生成上下文中的确认偏误，但独立模型不保证真理，所以仍需要证据、确定性检查和人工责任。

B 与 C 交换的是公共可检查证言，而不是私人心理状态。角色权威来自证据、校准和可复核性，不来自岗位名称、模型自信或语言流畅度。这里还必须区分内部因果计算、Agent 主动给出的自我说明，以及可以支持公共裁决的正当化理由。

合同中有两类规则：构成性规则决定一份输出是否仍算同一知识的合格转译，规制性规则决定已经合格的转译如何更清楚、更简短或更适合销售。构成性规则优先于风格、简洁、速度和销售偏好。Fresh/Repair 三分支体现转译的欠决定性与多重可实现性：同一合同可能有多份合格表达，但“多份可行”不表示任一表达都可接受。

### 17.6 通过、真与组织有效性

```text
Publishable(x) iff RequiredReview(x) is satisfied
                  and R_C(x, K_t, E) = pass when C is required
                  and P(x) = allow
                  and J_A(x) = publish
```

`Publishable(x)` 是制度谓词，不等于 `True(x)`。真实性仍依赖证据质量、时效、合同解释和外部世界。

### 17.7 记忆与同一性

A 的连续性不是把无限文本塞进单一上下文，而是通过原始事件、结晶、谱系和版本维持制度身份。B/C 的任务实例可以短暂变化，而岗位章程和历史通过 A 保持可追溯的组织同一性。

分析哲学上还需区分四种地位：档案真实性（某记录是否确为系统当时记录）、命题真值（内容是否符合外部世界）、认识地位（当时是否有充分理由相信）和制度地位（是否经程序获准使用）。总库完整性不推出真值完整性、检索完整性或认知完整性；所有认识承诺原则上都可被新证据击败。

### 17.8 D 的反思均衡

D 将个案判断、一般规则和结果指标放入受控的反思均衡过程。它可以指出规则与实践的张力，但不能仅凭统计成功改写规范；事实准确、数据权利和硬门槛优先于转化率。

Skill 对应 `knowing-how`（知道怎样做），知识库主要对应可证成的 `knowing-that`（知道什么）。系统内部判断“易懂”仍不足以证明真实用户理解，最终应通过目标受众理解测试、任务完成率和误解案例评测。承认证成不足并停止自动回答，是可靠认识制度的积极能力，不是系统失败的掩饰。

## 十八、勤益客服的输出规范

### 18.1 普通咨询

- 以正常聊天频率回复。
- 用户提出的上限目标为 30-45 秒；当前服务端默认总预算为 40 秒，浏览器最迟约 45 秒结束等待。
- 原始建议篇幅为约 200-300 个中文字；当时间不足时可以进一步缩短。
- 简单咨询优先给出直接答案、必要依据和一个自然的下一步问题。
- 无可靠知识命中时明确说明依据不足，不让模型凭自身知识猜测。

### 18.2 专业咨询

- 聊天输入框旁提供“专业咨询”开关。
- 开启后允许更多分析，不再把短篇幅作为主要目标。
- 建议 200-600 个中文字；硬上限 800 字。
- 当前服务端默认总预算为 55 秒，以适配 60 秒函数限制；专业模式不应被误解为无限等待。
- 专业模式只改变分析深度、篇幅和时间预算，不改变任何硬门槛、C 启动规则或公司准入。

### 18.3 中英文与受众

系统支持中文、英文、自动语言和可选双语。受众可为普通、知情或专家层级。跨语言的重要规格翻译属于硬门槛，应启动独立 C；普通文案翻译仍须保持模态、数量、单位和条件。

### 18.4 等待进度条

生成期间展示进度条，按已等待时间和可观察阶段推进，最多停在 92%，收到结果后结束并移除。它不是模型内部的精确完成百分比，界面不得伪称能看见模型真实思考进度。超时后应明确结束等待并返回安全结果或人工路径。

## 十九、四个 API 窗口与提供方隔离

每个 Agent 保留可改变、可独立配置的窗口：

```text
AGENT_A_PROVIDER / API_KEY / BASE_URL / MODEL / CHARTER_VERSION
AGENT_B_PROVIDER / API_KEY / BASE_URL / MODEL / CHARTER_VERSION
AGENT_C_PROVIDER / API_KEY / BASE_URL / MODEL / CHARTER_VERSION
AGENT_D_PROVIDER / API_KEY / BASE_URL / MODEL / CHARTER_VERSION
```

骨架和共享思想层保持 provider 无关：合同编译、风险分类、审核协议、返工、记忆、日志、通信和公司准入均在 provider 之外；提供方只负责各自窗口中的模型生成。不同窗口可以使用相同厂商或相同模型，但必须是独立实例、独立身份和独立上下文，不能因此退化为一个 Agent 跑完全程。

工程支持远程 OpenAI 兼容接口以及本地 Mock 测试替身，没有实现 Ollama 运行路径。实际运行使用哪种 provider 应以部署环境的非公开配置和状态接口为准，不能仅凭代码仓库推断。四个窗口如配置凭据，只能使用本地秘密或正式密钥管理系统；密钥本身不能进入本文、Git、前端、日志或截图。最终审核责任仍属于人类。

## 二十、非技术经营者界面

### 20.1 产品原则

界面面向不懂 AI 和网站编程的经营者。应使用业务语言呈现“当前发生什么、需要决定什么、决定后有什么影响”，隐藏模型参数和代码细节；高风险动作提供预览、解释、确认和回滚。

### 20.2 管理员工作面

目标能力包括：

- 查看等待人工、今日会话、待审核内容和提醒。
- 查看会话、客户已知信息和人工接管摘要。
- 认领、回复、等待客户、解决和关闭人工服务。
- 维护重要资料、内容草稿、审核、批准、发布和停用。
- 配置 AI 启停、`observe/draft/auto/paused` 模式和人工优先规则。
- 查看审计事件和通知设置。
- 未来连接企业微信、千牛、邮件、短信和钉钉；当前未配置的渠道只能显示为未启用，不能声称已真实通知。

### 20.3 开发者工作面

目标能力包括 Agent 公司状态、执行追踪、证据/审核摘要、发布版本、环境、集成检查、应急暂停和回滚。开发者能力必须使用更高权限，不能与普通运营或客户身份混用。

### 20.4 认证与权限

当前本地运营核心支持账号密码登录、短期 Bearer 会话和角色检查；开发者事件入口另用独立令牌。登录接口有独立频率限制，成功与失败均进入审计。客户聊天身份绝不能成为后台管理权限。生产环境还需要可信身份系统、最小权限、会话撤销、秘密管理和安全审计。

从目标制度看，人工拥有暂停、否决、接管、纠正、删除/封存、批准 L2 特权访问、批准 D 提案、发布和回滚的权力。当前对“最终审核由人工负责”的一致解释是：人类承担制度、高风险结果和生产治理的终局责任，并可否决任何自动结果；获批规则下的普通低风险回复可以自动发布。若要求每条普通回复都人工逐条终审，将与 30-45 秒自动回复和 `auto` 模式直接冲突，届时必须另设全量人工队列，不能在文档中假装两者同时成立。

### 21.3 当前运营核心

`OPERATIONS_ENABLED=false` 时不改变原客服开发/公开部署行为。启用后，本地单机适配器使用原子替换的 JSON 快照保存对话、消息、人工队列、联系人、通知、内容修订、系统配置和认证会话，并把审计、客服和 Agent 事件追加到 `events.ndjson`。

此实现适合有持久磁盘的本地或单服务器开发验收，不适合把临时文件系统当作 Vercel 生产数据库。后续应保持服务接口，替换为真实数据库、队列和通知适配器。

运营认证的实际细节是：密码使用 Argon2id，并以 scrypt 作为部署兼容回退；会话令牌随机生成，服务端只存 HMAC，带固定有效期并有注销端点。未知账号仍执行固定成本密码校验，登录接口另有频率限制。存储目录和新文件设置受限权限，快照采用临时文件、同步和原子重命名，单进程内用队列串行写入。这些措施提高本地可靠性，但快照正文仍是本地明文，事件文件也只是应用层追加，不是经过哈希链、签名、WORM 或权限分离保护的密码学不可篡改账本。

- `service-playbook/` 中的脱敏回复结构和权限经验只指导过程，不作为事实知识。
- 没有可靠匹配且没有允许的工具结果时直接说明依据不足。
- 订单和人工工单目前仍包含开发/演示适配器；运营核心开启后人工请求可持久化为本地 `OPS-` 服务请求，但不等于真实外部客服已收到通知。

## 二十二、安全、隐私、删除与审计

1. API 密钥、会话秘密和开发者令牌只在秘密存储中使用。
2. 前端、Git、文档、日志、知识库、事件正文和截图不得出现密钥。
3. 请求限制长度、频率和超时，日志遮蔽授权头、Cookie、客户消息正文等敏感内容。
4. 会话、订单和工单均绑定租户、用户和会话身份，禁止跨租户读取。
5. 发送给模型的用户标识使用 HMAC 匿名化。
6. 公开 CORS 白名单不等于身份认证；生产应由可信网关重写身份头。
7. 客户删除、授权撤回、法律要求和数据更正优先于默认无期限保留。
8. 删除必须覆盖当前会话、总库事件和所有依赖结晶；只保留不含正文的删除审计证明。
9. PII 遮蔽函数不能替代数据最小化、供应商协议、地区/保留评审和人工治理。
10. 对 L2、跨客户、批量和训练抽取的访问必须记录申请人、目的、范围、批准人、时间和结果。

- L1 目前能够写入脱敏结晶，但尚无按岗位、领域和任务自动检索/召回结晶与 Skill 的完整接口；记忆默认关闭。第五、十四、十六章描述的是目标访问制度，不表示现有 B/C 已自动获得历史经验。
- 当前 B 主要返回候选、引用和运行元数据，尚未完整生成第十五章所定义的结构化显式理由报告。当前 D 接收阶段样本、风险和问题代码，尚不能对每次 Fresh-1/Fresh-2/Repair 的正文与审核作完整逐项重建比较。
- L2 的生产级数据库、细粒度批准工作流、密钥轮换和合法保留策略尚未完成。
- 管理/开发页面是本地运营核心，外部通知渠道、真实人工客服系统和真实订单系统尚未接通。
- 运营指标中的真实延迟、错误率、告警和事故目前仍需生产遥测支持。
- 规则测试、发布和应急动作中有兼容/演示性质的行为，不能在未审查前直接视为生产控制面。
- 重要跨语言规格的专业词典、单位规范、数值一致性和双人复核策略仍需业务金标集验证。

### 24.4 当前运营原型的逐项缺口

以下均应在对外宣称“非技术用户可独立运营”或正式生产前处理：

1. 后台 RBAC 仍较粗。开发者页面区分 `developer/system_owner`，但一般后台多数接口只检查“已登录”，客服角色也可能读取全量会话、联系人、审计并修改规则、配置和内容状态。
2. 后端支持多用户名，当前登录界面却没有用户名输入，默认只尝试 `admin`；页面也尚无注销按钮，虽然后端已有注销端点。
3. 认领人与当前操作者的绑定不完整，多账号并发接管和回复还没有形成严格所有权闭环。
4. 运营快照中的消息和联系方式没有静态加密，只有部分人工摘要做 PII 遮罩。
5. 客户删除会话时，思想层会话可删除，但运营库目前主要把对话标为关闭，没有级联清理消息、联系人、工单和事件，因此尚未达到本文第十四、二十二章的删除制度。
6. 客户事件入口允许较宽的事件类型和 payload，尚需白名单、内容脱敏和更严格的大小/隐私控制。
7. “重要信息”目前只是系统配置中的草稿，没有发布状态，也没有进入知识库、B 合同或 C 审核，因而不会自动成为回答事实。
8. 内容模块目前可创建草稿和改变状态，但缺少完整正文编辑、合法状态迁移、审批职责隔离、真实网页预览和部署；当前前端的部分预览/筛选动作与后端状态命名还不一致。
9. 开发者页面中的批准、驳回和回滚目前主要改变内容状态，不等于代码/网站部署或真实文件回滚，部分前端确认字段也未在服务端强制校验。
10. 企业微信、千牛、邮件、短信、钉钉只是未配置的渠道占位，没有真实发送器；通知设置的前后端数据形状仍需统一。
11. 客服规则除运行模式外尚未全面接入 ABCD 决策；规则测试还是固定关键词示范，保存的人工条件和说明未成为规范合同或公司政策，默认规则结构与界面期望也需统一。
12. Agent 追踪当前依赖外部事件入口写入，没有自动连接每一次真实 ThoughtLayerEngine 执行；详情中的证据和审核摘要仍是占位，不能称为完整真实链路。
13. 系统错误率、P95、事故和部分环境状态仍是固定展示；“验证集成”目前主要记事件，不是真实外部连接诊断。
14. 应急暂停/恢复能改变 `aiEnabled/operatorMode`，但恢复前尚无真实健康检查，界面提交的二次确认也需由服务端强制验证。
15. 审计导出端点尚未实现，界面筛选字段与后端事件映射还不完全一致。
16. 文件存储的进程内队列不能协调多实例；快照和追加事件之间也不是一个跨文件不可分割事务，需要数据库事务或可靠事件机制。
17. 一个租户与访客的多个浏览器会话可能聚合到同一未关闭运营会话，需根据正式业务决定是一访客一连续会话还是一 session 一会话。

### 24.5 质量评价框架

B 应分别评测事实忠实、指称忠实、推论/因果忠实、模态忠实、证据忠实、信息完整性、易懂性和用途适配。C 应评测漏检率、误拒率、证据质量、重复审核一致性和已知植入错误发现率。D/Skill 更新必须使用独立保留集与历史回归，不能让系统只用自身循环评分证明自己正确。

测试范围应继续覆盖普通 B-only、高风险 C、首次失败三候选、三轮失败转人工、C 盲审隔离、公司准入不可绕过、合同状态与版本迁移、L0/L1/L2 权限、删除级联、专业模式篇幅、前后端超时、进度条、跨租户、提示注入、四 API 窗口隔离，以及 D 不能自动上线。真实模型、Redis、真实订单/工单和公网部署仍需隔离预发布验证。

## 二十五、表面冲突的统一解释

1. **原初流程“B 后交 C”与客服“普通咨询只走 B”**：前者是高保证基线，客服实现采用风险分层；普通答复仍过确定性 C0 和公司准入，高风险才调用独立 C。
2. **“只运行 B/只运行 C”与 A 始终存在**：只运行指生成/审核模型阶段互斥；A 的编排、日志和公司准入不停止。
3. **B/C 保存完整工作记录与“不保留历史”**：任务期间产生完整显式记录，长期档案由 A 保存；B/C 实例本身没有私有永久记忆。
4. **保存全部内心推理与模型隐藏思维不可见**：保存显式理由报告和执行轨迹，不虚构或索取不可见 chain-of-thought。
5. **总库绝对完全、永久与删除权**：完整限定为系统可观察且依法允许保存；永久指默认无期限，服从删除、撤权、法律和更正。
6. **A 可破例与硬门槛不可覆盖**：不存在绕过式破例，只能补证、重新订约和重新生成，直到 C 按原标准通过。
7. **A 最终决定与人工最终负责**：A 在授权自动范围内作组织裁决；人类保有终局否决、接管、治理审批和法律责任。当前不声称每条普通回复都逐条人工预审。
8. **岗位输出不受大规则影响与岗位仍受合同约束**：岗位按自己的规则和合同生成原始产出，公司层不篡改它，但可禁止其形成产品或发布。
9. **D 经 A 决定更新与人工批准**：完整链路是 D 提案、A 证据裁决、人类生产批准；A 不静默发布高影响 Skill。
10. **合同随会话变化与单次执行稳定**：跨轮版本化改变，单次运行冻结；新信息形成新版本。
11. **普通 200-300 字与超时缩减**：前者是内容偏好，后者是时间约束下的安全降级，事实和审核优先。
12. **专业咨询不多考虑字数与 800 字上限**：不追求极短，但仍以 200-600 为优选、800 为硬上限。
13. **普通 30-45 秒与专业 55 秒**：用户时限针对简单普通咨询；55 秒是专业模式的当前工程预算。
14. **当前只做本地版与文档中的 Pages/Vercel**：前者是当前交付边界，后者只是未来公网方案。
15. **四 API 独立与可用同一提供方**：独立性来自身份、上下文、权限和配置窗口，不强制四家厂商；生产仍建议独立轮换凭据。
16. **Provider 只负责生成与 A/C/D 也可调用模型**：“生成”广义指无状态计算输出；制度效力、合同、状态、记忆和准入始终在 provider 外。
17. **“E”**：E 是需求—供给虚化嵌合方法，不是第五个 Agent。
18. **L2 四类回源与人工审批**：投诉、接管、证据冲突、审计只表示允许提出单会话目的受限回源，仍须逐次记录；跨客户、批量、联系方式、历史订单和训练抽取必须明确人工批准。

## 二十七、不可协商不变量

1. ABCD 是四个独立制度 Agent，不得退化成一个 Agent 轮换 Prompt。
2. A 不生成客户正文，C 不替 B 生成，D 不介入实时对话。
3. 公司制度不替岗位悄悄改写产出，只决定路由、准入、返工和发布。
4. 未满足所需审核条件的产品不能对客发布。
5. A 不能命令 C 通过；“破例”只能通过证据和重新生成形成真正可通过的产品。
6. 硬门槛不能被模型、B2/C2、客户画像或销售临时要求覆盖。
7. B 与 C 不共享彼此的私有历史，只通过 A 的最小结构化交接协作。
8. Fresh 分支不读取旧稿和审核原因；Repair 才读取过滤后的问题。
9. 三轮失败后转人工，并生成完整已知信息报告。
10. 原始记录与结晶并存；蒸馏只替代活动上下文中的原文，不抹除总库原文。
11. 默认无期限归档服从删除、撤权、法律和更正权，且必须级联撤销结晶。
12. D 只提案；生产 Skill 和规则变更需要 A 审议、人类批准、评测与回滚。
13. provider 只负责模型执行，不维护一套可绕过的独立业务规则。
14. 四个 API 窗口可替换，但公司骨架、共享思想层和最终人工责任不随提供方变化。
15. 专业咨询不绕过风险、证据、C 或公司准入。
16. 进度条只表达可观察等待阶段，不伪装为模型真实思维进度。
17. 任何秘密不得进入 Git、前端、文档、知识、日志或截图。
18. 超时或取消后的迟到候选不得发布、污染会话已接受状态或产生迟到准入副作用。

## 二十九、术语表

- **产品**：某岗位的输出经过后续制度处理后形成的可交付物；岗位原始输出不必然是产品。
- **语义合同**：客户目标、事实、限制、不确定性和输出义务的可修订结构。
- **硬化**：把经客户确认和证据支持的候选字段变成明确合同或生产规格。
- **虚化/抽象**：去除表面叫法，提取功能与约束；不等于模糊事实。
- **嵌合**：在需求和供给间建立证据支持的部分接口映射。
- **C0**：非独立 Agent 的确定性预检，是公司准入工具的一部分。
- **独立 C**：使用独立身份、上下文和窗口的审核 Agent。
- **结晶**：从原始事件蒸馏出的脱敏、可调用、带谱系经验。
- **总库/L2**：可观察原始记录的完整加密档案。
- **即时库/L1**：面向当前任务自动召回的脱敏结晶库。
- **Skill**：经治理批准的程序性能力，不是事实来源。
- **组织有效性**：候选依程序获得发布许可；不等于逻辑或经验上的绝对真理。
- **人工最终责任**：人类对高风险决定、规则变化、例外、数据权利和生产结果保有最终权力与责任。
